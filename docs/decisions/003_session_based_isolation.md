# ADR-003: Session-Based File Isolation

**Date:** 2024-01-20 (Estimated - Early Phase 1)
**Status:** Accepted
**Deciders:** Development Team, Security Engineer
**Tags:** security, file-management, session-management, isolation

---

## Context

### Problem Statement

The biomedical image segmentation application handles large files (100+ MB TIFF stacks) and generates trained models. We needed to decide how to organize and isolate files for different users and workflows.

**Requirements:**
- **Security:** Users should not access each other's files
- **Organization:** Clear file organization for debugging
- **Concurrent workflows:** Support multiple workflows simultaneously
- **Easy cleanup:** Ability to reset/clear user data
- **Debugging:** Easy to trace files to specific workflows

### Background

**File Types to Manage:**
- **Uploads:** Training images, annotations, inference images (100-500 MB each)
- **Models:** Trained PyTorch models (.pth files, 10-100 MB)
- **Results:** Segmented images, metadata, visualization data (100-500 MB)
- **Total per workflow:** 1-2 GB of files

**Usage Patterns:**
- Users may run multiple workflows concurrently
- Same user may use different browsers/devices
- Training takes 10-30 minutes (files in use)
- Results may be downloaded multiple times
- Users may reset and start over

### Current State

This decision was made at the **beginning of Phase 1** when designing file storage architecture. No previous file organization system existed.

---

## Decision

**We have decided to use session-based file isolation (files organized by session ID) rather than user-based (by username) or global storage.**

### Details

**Directory Structure:**
```
uploads/<sessionId>/
   ├─ 1637012345-training.tif
   ├─ 1637012346-annotation.tif
   └─ 1637012347-inference.tif

models/<sessionId>/<trainingId>/
   ├─ best_model.pth
   ├─ config.json
   └─ results.json

results/<inferenceId>/
   ├─ segmented.tif
   ├─ metadata.json
   └─ visualization.json
```

**Session ID:**
- Generated by express-session
- Format: Cryptographic hash (32+ characters)
- Example: `a3f7b2e8c9d1...`
- Stored in HTTP-only cookie
- Persists for 7 days

**File Path Construction:**
```javascript
// multer configuration
destination: function (req, file, cb) {
  const sessionId = req.session.id;
  const uploadDir = path.join('uploads', sessionId);

  if (!fs.existsSync(uploadDir)) {
    fs.mkdirSync(uploadDir, { recursive: true });
  }

  cb(null, uploadDir);
}
```

**File Access Pattern:**
```javascript
// Always use session ID for file paths
const trainingPath = path.join('uploads', req.session.id, 'training.tif');
const modelPath = path.join('models', req.session.id, trainingId, 'best_model.pth');
```

## Alternatives Considered

### Option 1: Global Uploads Directory (No Isolation)

**Description:**
All files stored in single directory with no user isolation.

```
uploads/
├─ 1637012345-training.tif
├─ 1637012346-annotation.tif
├─ 1637012347-user2-training.tif
└─ 1637012348-user2-annotation.tif
```

**Pros:**
- ✅ Simplest implementation
- ✅ Easy to find all files
- ✅ No directory structure needed

**Cons:**
- ❌ **Security:** No isolation (users could guess file names)
- ❌ **Cleanup:** Hard to delete user-specific files
- ❌ **Organization:** Messy, thousands of files in one directory
- ❌ **Debugging:** Can't trace files to users/sessions
- ❌ **Conflicts:** Filename collisions possible

**Why not chosen:**
Major security and organization issues. Users could potentially access each other's files. No way to organize or clean up.

---

### Option 2: User-Based Directories

**Description:**
Files organized by username.

```
uploads/<username>/
   ├─ training.tif
   ├─ annotation.tif
   └─ inference.tif

models/<username>/<trainingId>/
   ├─ best_model.pth
   └─ config.json
```

**Pros:**
- ✅ Good isolation per user
- ✅ Easy to find user's files
- ✅ Simple to understand
- ✅ Easy cleanup (delete user directory)

**Cons:**
- ❌ **Concurrent workflows:** User can't run multiple workflows simultaneously
- ❌ **Multiple devices:** User on laptop and desktop share same directory (conflicts)
- ❌ **File conflicts:** Upload new training file → overwrites old one
- ❌ **Session independence:** Can't have separate browser sessions
- ❌ **Predictable paths:** Username is predictable (security issue)

**Why not chosen:**
Doesn't support concurrent workflows. User on multiple devices would conflict. Username is less secure than session ID.

---

### Option 3: Session-Based Directories (Chosen)

**Description:**
Files organized by session ID (Express session).

```
uploads/<sessionId>/
models/<sessionId>/<trainingId>/
results/<inferenceId>/
```

**Pros:**
- ✅ **Strong isolation:** Session ID is cryptographic hash
- ✅ **Concurrent workflows:** Each session gets own directory
- ✅ **Multiple devices:** Different browser/device = different session
- ✅ **No conflicts:** Separate directories for each session
- ✅ **Easy cleanup:** Delete session directory on reset
- ✅ **Security:** Session ID harder to guess than username
- ✅ **Debugging:** Trace files to specific session
- ✅ **Session reset:** Clear all files for session easily

**Cons:**
- ⚠️ **Files lost if session expires:** 7-day expiry
  - **Mitigation:** 7 days is long enough for typical workflows
  - **Mitigation:** Users download results immediately

- ⚠️ **Orphaned files if server restarts:** express-session in-memory
  - **Mitigation:** File-based session storage (Phase 1 fix)
  - **Future:** Periodic cleanup job for orphaned files

- ⚠️ **User can't find files across sessions:** Different session = different directory
  - **Acceptance:** Intended behavior - sessions are isolated
  - **Future:** User-based file browser (Phase 3+)

**Why chosen:**
Best fit for requirements. Supports concurrent workflows, strong isolation, easy cleanup, and good security. Trade-offs are acceptable.

## Consequences

### Positive (Benefits)

- ✅ **Strong Isolation:** Cryptographic session IDs prevent unauthorized access
- ✅ **Concurrent Workflows:** Same user can run multiple training/inference workflows simultaneously
- ✅ **Multi-Device Support:** User on laptop + desktop = separate sessions, no conflicts
- ✅ **Easy Session Reset:** Delete session directory to clear all files
- ✅ **Clear Debugging:** Session ID traces files to specific workflow
- ✅ **No File Conflicts:** Each session has its own directory
- ✅ **Security:** Session ID harder to guess than username

### Negative (Trade-offs)

- ⚠️ **Files Lost on Session Expiry:** 7-day TTL, then files may be orphaned
  - **Mitigation:** Long enough for typical workflows (training takes <1 hour, user downloads results immediately)
  - **Acceptance:** Research workflows are short-lived

- ⚠️ **Orphaned Files on Server Restart:** In-memory session data lost
  - **Mitigation Phase 1:** File-based session storage (persists across restarts)
  - **Future:** Redis session storage for production
  - **Future:** Periodic cleanup job for old files

- ⚠️ **User Can't Access Files from Other Sessions:** Sessions are isolated
  - **Acceptance:** Intended behavior (security feature)
  - **Future:** User-based file browser (Phase 3+) to view all user's files

- ⚠️ **Nested Directory Structure:** More complex than flat structure
  - **Acceptance:** Worth it for organization benefits

### Neutral (Impacts)

- ℹ️ **Session ID in File Paths:** All file operations require `req.session.id`
- ℹ️ **Directory Creation:** Must create session directory on first upload
- ℹ️ **Cleanup Responsibility:** Need to clean up orphaned files eventually

## Implementation

### Changes Required

**1. Multer Configuration:**
```javascript
const storage = multer.diskStorage({
  destination: function (req, file, cb) {
    const sessionId = req.session.id;
    const uploadDir = path.join('uploads', sessionId);

    // Create session-specific directory
    if (!fs.existsSync(uploadDir)) {
      fs.mkdirSync(uploadDir, { recursive: true });
    }

    cb(null, uploadDir);
  },
  filename: function (req, file, cb) {
    const timestamp = Date.now();
    cb(null, `${timestamp}-${file.originalname}`);
  }
});
```

**2. File Path Construction:**
```javascript
// Upload endpoint
app.post('/upload-data', requireAuth, upload.fields([...]), (req, res) => {
  const sessionId = req.session.id;
  const trainingPath = path.join('uploads', sessionId, req.files.training[0].filename);
  const annotationPath = path.join('uploads', sessionId, req.files.annotation[0].filename);

  // Store in session
  req.session.uploadedFiles = {
    training: trainingPath,
    annotation: annotationPath
  };
});
```

**3. Model Storage:**
```javascript
// Training endpoint
app.post('/start-training', requireAuth, (req, res) => {
  const sessionId = req.session.id;
  const trainingId = uuidv4();
  const outputDir = path.join('models', sessionId, trainingId);

  // Create directory
  fs.mkdirSync(outputDir, { recursive: true });

  // Spawn Python with output path
  spawn('python', ['python/train_model.py', ..., outputDir]);
});
```

**4. Results Storage:**
```javascript
// Inference endpoint
app.post('/run-inference', requireAuth, (req, res) => {
  const inferenceId = uuidv4();
  const outputDir = path.join('results', inferenceId);

  fs.mkdirSync(outputDir, { recursive: true });

  spawn('python', ['python/run_inference.py', ..., outputDir]);
});
```

**5. Session Reset (Cleanup):**
```javascript
app.post('/reset-session', requireAuth, (req, res) => {
  const sessionId = req.session.id;

  // Delete session directories
  const uploadDir = path.join('uploads', sessionId);
  const modelDir = path.join('models', sessionId);

  if (fs.existsSync(uploadDir)) {
    fs.rmSync(uploadDir, { recursive: true, force: true });
  }

  if (fs.existsSync(modelDir)) {
    fs.rmSync(modelDir, { recursive: true, force: true });
  }

  // Clear session data
  req.session.uploadedFiles = null;
  req.session.trainingConfig = null;
  req.session.currentTraining = null;

  res.json({ success: true });
});
```

**6. File-Based Session Storage (Phase 1 Fix):**
```javascript
const FileStore = require('session-file-store')(session);

app.use(session({
  store: new FileStore({
    path: './sessions',
    ttl: 86400 * 7,  // 7 days
  }),
  secret: process.env.SESSION_SECRET,
  // ...
}));
```

### Migration Path

**No migration needed** - This was the initial design.

**Future Enhancements (Phase 3+):**
1. **User-Based File Browser:** UI to view all files across sessions
2. **Periodic Cleanup Job:** Cron job to delete old orphaned files
3. **Redis Session Storage:** For production, distributed sessions
4. **File Archiving:** Archive old training runs for later reference

## Notes

### Future Considerations

**Production Considerations:**
- Implement Redis for session storage (distributed systems)
- Add periodic cleanup job for orphaned files
- Monitor disk space usage
- Consider object storage (S3) for large files

**User Experience:**
- Add user-based file browser (Phase 3) to view all files
- Show session expiry warning to users
- Provide file archive/export feature

### Assumptions

- Users complete workflows within 7 days (validated)
- Disk space is not a constraint (valid so far)
- Server restarts are infrequent (valid)
- Users download results immediately (mostly valid)

### Lessons Learned

**What Worked Well:**
- Strong isolation prevents security issues
- Concurrent workflows work perfectly
- Easy debugging with session IDs
- Session reset is simple and effective

**What Could Be Better:**
- Orphaned files accumulate (need cleanup job)
- Users can't easily view all their past files (Phase 3 fix)
- Would benefit from user-level file organization layer

**Would We Make Same Decision Again?**
**Yes.** Session-based isolation was the right choice:
- Security benefits are significant
- Concurrent workflow support is essential
- Trade-offs (session expiry, orphaned files) are manageable
- Future enhancements (file browser, cleanup job) can address limitations
